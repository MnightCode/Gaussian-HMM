# Метрики зіставлення фаз — визначення ДО реалізації

Цей документ фіксує **точні визначення** метрик, якими після затвердження
`reports/market_phases_template.csv` (дати заповнює й підтверджує користувач,
не Claude) буде оцінено кожне вікно (`w1000`, `w2000`, `w3000`, `w5000`,
`all-history`, та, якщо буде, adjusted-варіант). Жодне обчислення ще не
запущено — це лише специфікація метрик для узгодження.

## Вхідні дані
- `reports/market_phases_template.csv` (заповнений і затверджений):
  `phase_id, expected_regime, start_date, end_date, rationale_source`.
- `reports/daily_replay_w*_timeline.csv` — уже обчислені сирі щоденні рішення
  (`decision_date`, `raw_decision`, ...). Нових HMM-прогонів не потрібно.

## Метрики (по кожній фазі, по кожному вікну)

1. **`first_matching_decision`** — найраніша `decision_date` у межах
   `[start_date, end_date]` фази, де `raw_decision == expected_regime`.
   `None`, якщо жодного разу не збіглося.
2. **`detection_delay`** — `first_matching_decision − start_date` (у торгових
   днях). Від'ємне значення неможливе за конструкцією (перше зіставлення не
   може бути раніше `start_date`, оскільки пошук ведеться в межах
   `[start_date, end_date]`); якщо потрібно перевірити випередження — окреме
   питання, не рахується цією метрикою.
3. **`last_matching_decision`** — найпізніша `decision_date` в межах фази, де
   `raw_decision == expected_regime`.
4. **`exit_delay`** — `end_date − last_matching_decision` (у торгових днях):
   наскільки рано модель «перестала» видавати очікуваний режим до
   фактичного завершення фази (не після — вихід ПІСЛЯ `end_date` окремою
   метрикою не рахується цим документом, оскільки `end_date` вже задає межу
   вікна пошуку; пізні підтвердження після `end_date` можна порахувати
   окремо, якщо знадобиться).
5. **`matching_days_count`** — кількість днів у фазі, де
   `raw_decision == expected_regime`.
6. **`neutral_days_count`** — кількість днів у фазі, де `raw_decision ==
   'neutral'`.
7. **`opposite_signal_count`** — кількість днів у фазі, де `raw_decision`
   дорівнює **протилежному** режиму (наприклад, `bear` у межах фази з
   `expected_regime == BULL`, або навпаки).
8. **`longest_matching_streak`** — найдовша послідовність **послідовних
   торгових днів** (за `decision_date`, не обов'язково без прогалин по
   календарю — саме послідовних рядків у таймлайні) у межах фази, де кожен
   день має `raw_decision == expected_regime`.
9. **Дві ведмежі фази як дві окремі події** — перевіряється буквально: чи
   `matching_days_count > 0` окремо для `phase_id=1a` і окремо для
   `phase_id=1b` (кожна ведмежа фаза — свій рядок у таблиці фаz, свої
   метрики; НЕ об'єднується в одну).

## Що ця специфікація НЕ робить
- Не визначає, яке вікно «краще» — просто рахує ці метрики по кожному вікну
  окремо, для порівняння фактів.
- Не називає жодну фазу «розпізнаною» на основі одного відсотка — саме для
  цього вводяться `first/last_matching_decision`, `detection_delay`,
  `exit_delay`, `longest_matching_streak`.
- Не вигадує дати фаз — вони приходять виключно з затвердженого
  `market_phases_template.csv`.

## Порядок дій
1. Користувач заповнює `start_date`/`end_date`/`rationale_source` у
   `reports/market_phases_template.csv`.
2. Якщо визначення метрик вище потребують правок — правимо цей документ.
3. Лише після затвердження — реалізація одного скрипту, що читає вже наявні
   `*_timeline.csv` (без нового HMM-прогону) і рахує ці метрики по кожній
   фазі й вікну.
